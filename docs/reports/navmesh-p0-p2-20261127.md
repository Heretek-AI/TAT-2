## 2. The 221 -> 80 merge (and the per-map numbers)

The raw off-mesh records are directional copies of the same physical link plus
parallel copies split by poly/tile borders. `parse_nav.py` applies, in order:

1. exact duplicate unordered endpoint pairs collapse (221 -> **123** pairs for
   Guildhall), keeping the direction census;
2. parallel copies (`|dot| >= 0.99`) within **150 cm** perpendicular separation
   and overlapping along the link direction merge into one logical link
   (123 -> **80**);
3. the canonical endpoint pair is the most duplicated copy; a one-way link
   keeps its authored A->B direction. A link is `bidirectional` **only** when
   both directions appear in the census, never from the raw flags (all observed
   records carry flag 64).

| map | raw records | exact pairs | logical links | bidirectional | one-way |
|---|---:|---:|---:|---:|---:|
| Guildhall | 221 | 123 | **80** | 35 | 45 |
| Old Manor | 216 | 113 | **64** | 15 | 49 |
| FTUE | 11 | 8 | **4** | 0 | 4 |

Do not create one `NavigationLink3D` per raw record; the 221/216/11 counts are
records, not links.

## 3. Areas are per-map and 63 is walkable

`NavArea_Default` is authored id **63** in every map and must never be treated
as Recast's null area. The class table is read from each map's own
`SupportedAreas`; the ids are not a global list.

| map | Default 63 | Obstacle 1 | LowHeight 62 | PrivateArea 2 | Bushes | Door |
|---|---:|---:|---:|---:|---:|---:|
| Guildhall | 14,558 | 7 | 0 | 0 | **3** (144) | **4** |
| Old Manor | 8,874 | 0 | 0 | 0 | **4** (185) | **3** |
| FTUE | 5,575 | 1 | 0 | 0 | **3** | **4** |

`NavArea_Null` (0) has no walkable poly; the parser refuses an area-0 polygon.
The runtime rejects a binary whose poly area byte is 0.

## 4. N-P1 — runtime region

`game/src/ai/nav_runtime.gd` (new, 218th checked script):

- one `NavigationMesh` + one `NavigationRegion3D` per map from the authored
  binary; `vertices` + `add_polygon`, no bake;
- map settings applied **before** the region enters the server map:
  `cell_size=0.01`, `edge_connection_margin=0.05`,
  `link_connection_radius=1.0`;
- `TAT2_NAV=off|on` (default **off**); `TAT2_NAV_DIR` overrides the asset root
  for probes;
- `setup(map_id)` fails closed (returns false, logs one warning) on a missing
  manifest, missing map, bad magic/version/counts, a 0 area, a poly outside
  3–6 vertices, trailing bytes, or manifest/binary count mismatch;
- `wait_ready()` waits until the map has an iteration id, at least one region,
  and a mesh point answers (the spike measured 1.0–1.5 s / 67–92 physics
  frames; the runtime probe measured `frames=74..79 ready_ms=1078..1158
  build_ms=30..35` across runs on this host);
- `clear()` removes the region and every link, called at `start_contract()` and
  `_exit_tree()` so a reload cannot stack regions.

`mission_controller.gd` now spawns the swinging doors **before** guards, then
awaits `_start_nav_runtime(map_id)` (guards spawn only after `map_ready`), then
registers door links, then runs the existing guard/loot spawns. Doors are
independent of guards; the Den hub skips the runtime (no generated asset).
When `TAT2_NAV` is off or the asset is missing, the old straight-line
`nav_steering` path is unchanged.

## 5. N-P2 — links and doors

- the 80 Guildhall logical links (64 Old Manor, 4 FTUE) become
  `NavigationLink3D`s; `bidirectional` comes from the census, not the raw flag.
  The authored radius/height (100/100 cm for 203 Guildhall records, 30/60 for
  18) are stored per link in the binary; Godot 4.7's `NavigationLink3D` has no
  per-link radius/height, so the consumer uses the map's 1.0 m
  `link_connection_radius` and keeps the authored values for a future custom
  traversal cost;
- `start_position`/`end_position` are set **before** `add_child()`; the
  navigation server registers a link on enter and does not re-read a
  post-enter position write (measured: the first door-link attempt was enabled
  but still produced the 3.58 m partial path; moving the position write before
  enter is the fix);
- door links come from the real `swinging_doors` group nodes: the opening
  centre is the average of the leaf pivot positions, the normal is the
  averaged authored leaf plane normal (`basis.z`), and the two endpoints are
  the centre `+/-2.2 m` along that normal (the spike's measured doorway sample;
  1.25 m stays inside a thick prison opening). The endpoints are snapped with
  `map_get_closest_point`; a side whose snap is **>2.5 m** skips the whole door
  (no floating link);
- a door link is enabled only while **every** leaf of that actor reports
  `open_angle_deg() > 70`; the co-located `NavLinkFront/Back` actors are not
  used;
- the prison door east->west path is partial with the link off
  (`waypoints=4 length=3.58 m straight=4.91 m reach=1.33 m`) and completes with
  the link on (`reach=0.00 m`).

## 8. Risks and open items

### N-P3 tasks (from the independent verification)

- **Link direction census (merge-blocking for the N-P3 parity claim).** The
  emitted 35/45 split is not the full direction census: **43 of Guildhall's 45
  one-way links, 45/49 Old Manor and 4/4 FTUE have an opposite-direction
  parallel copy** that `tools/parse_nav.link_census` ignores because it only
  counts the exact canonical reverse. The 150 cm merge therefore either
  collapses one physical link (then those links should be bidirectional) or
  combines two one-way lanes (then the merge itself is the issue). N-P3 must
  decide with the authored evidence and re-measure; do not silently flip the
  flags.
- **Manifest/binary link count.** `nav_runtime.setup()` compares manifest
  `polys` and `verts` to the binary but not manifest `links` to the binary
  `link_count`; add that fail-closed check in N-P3 (the current assets agree at
  80/64/4).

- **Multi-floor / vertical:** the authored mesh is one region with all floors.
  Paths can change floors only through authored polys/links; the one-way drop
  link `NavLink_71` (Guildhall; both endpoints ~6 m from the cooked mesh) cannot
  connect in Godot and is kept as authored data. No parity/live run has measured
  guard trajectories yet.
- **Closed-door one-way baked link:** Guildhall's prison off-mesh record is a
  one-way (-X -> +X) baked link that is always enabled. The new bidirectional
  door link is state-gated and covers the tested east->west direction; the
  baked one-way direction can still cross a closed prison door. Binding
  door-tied baked links to the owning door is an open N-P3 decision.
- **Door windows:** the Guildhall `swinging_doors` group includes window
  pivots; their links stay disabled (they never pass 70 degrees) and count as
  door groups. Only the real doors change state.
- **Door-link coverage:** the real Guildhall boot created 42 links from 80
  door groups and skipped 38 by the 2.5 m snap (windows, doors outside the
  authored navigable area, non-navigable upper rooms). No per-actor audit has
  proven that every route-critical door is in the 42; N-P3 should list the
  skipped actors and decide each (normal orientation / midpoint / no-navmesh)
  rather than widening the 2.5 m limit silently.
- **Global map settings:** `cell_size` / `edge_connection_margin` /
  `link_connection_radius` are per navigation map. The port has no other
  regions; a future region must not assume the 0.25 m defaults.
- **Load cost:** +0.865–1.215 s ready (0.894–1.245 s including build) measured
  before guards spawn when enabled (headless; 57–79 frames). The mission already
  awaited the async sublevel load; this is an added synchronous mesh build on
  the main thread (29–35 ms build + server sync).
- **Old Manor / FTUE runtime:** the per-map asset build is probed (Old Manor
  9,059 polys / 64 links / 15 bidirectional; FTUE 5,576 / 4 / 0), but no
  doorway/path/door-link test has run on those maps.
- **No GPU / no parity claim:** no Vulkan/Xvfb/Route run in this lane; the
  default is off, and `TAT2_NAV=on` is the only way to change AI movement.
